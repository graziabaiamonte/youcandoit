Frameworks promise agents in five lines of code. They also hide the prompts, the loop and the
failure handling, which is exactly what you need to understand when an agent misbehaves at 2 a.m.
In this session you build a tool-using agent with nothing but the provider SDK and a `while` loop.
Once you have done it, every framework becomes readable: it is this loop with extras. Main
reference: [Claude tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview).
The [Hugging Face smol-course](https://github.com/huggingface/smol-course) is useful background on
the open-model side: its instruction-tuning material explains **chat templates**, the text format
in which open models actually see roles and tool calls.

## Tool definitions and schemas

A tool definition has three parts (session 9.1.4): a `name`, a `description` and an
`input_schema` (JSON Schema). For an agent, tool design is the biggest lever you have on quality.
Anthropic's [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
calls this the agent-computer interface and recommends investing in it as much as in a human UI.

Guidelines:

- **Describe when to use it, not just what it does.** "Search the web for current information.
  Use for facts that may have changed after your training data, or for sources to cite. Returns
  titles, URLs and snippets."
- **Name parameters unambiguously** and document formats: `"date": "ISO 8601, e.g. 2026-05-03"`.
- **Return what the model needs, compactly.** Ten results with 2,000-character snippets drown the
  context; five results with 300-character snippets and URLs usually suffice.
- **Make mistakes hard.** Use enums for closed sets, required fields, and validation with helpful
  error messages.
- **Few, distinct tools** beat many overlapping ones. If two tools could both answer a question,
  the model will sometimes pick the wrong one.

```python
TOOLS = [
    {
        "name": "web_search",
        "description": (
            "Search the web. Use for current facts or to find sources. "
            "Returns up to 5 results as JSON: title, url, snippet."
        ),
        "input_schema": {
            "type": "object",
            "properties": {"query": {"type": "string", "description": "Search terms, max 12 words"}},
            "required": ["query"],
        },
    },
    {
        "name": "calculator",
        "description": (
            "Evaluate an arithmetic expression exactly. Use for ANY maths instead of computing "
            "in your head. Supports + - * / ** ( ) and decimals."
        ),
        "input_schema": {
            "type": "object",
            "properties": {"expression": {"type": "string", "description": "e.g. (1250 * 1.22) / 12"}},
            "required": ["expression"],
        },
    },
]
```

On the code side, keep a registry mapping names to functions, so dispatch is one lookup:

```python
REGISTRY = {"web_search": web_search, "calculator": calculator}
```

> [!NOTE]
> Providers also offer **server tools** they run for you (Claude has web search and code execution
> tools, for example). They save work, but in this session you implement tools yourself so you see
> every step.

## The manual tool-use loop

The loop is the think-act-observe cycle from 9.5.1 written as code:

```python
import json
import anthropic

client = anthropic.Anthropic()
SYSTEM = (
    "You are a research assistant. Use web_search to find sources and calculator for every "
    "computation. Cite URLs for factual claims. When you have enough information, answer."
)

def run_agent(goal: str, max_steps: int = 10) -> str:
    messages = [{"role": "user", "content": goal}]
    for step in range(max_steps):
        resp = client.messages.create(
            model="claude-sonnet-5-5", max_tokens=2000,
            system=SYSTEM, tools=TOOLS, messages=messages,
        )
        messages.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason != "tool_use":          # model answered: we're done
            return "".join(b.text for b in resp.content if b.type == "text")

        results = []
        for block in resp.content:                  # there may be several tool calls
            if block.type == "tool_use":
                output, is_error = execute(block.name, block.input)
                results.append({
                    "type": "tool_result", "tool_use_id": block.id,
                    "content": output, "is_error": is_error,
                })
        messages.append({"role": "user", "content": results})
    return "Stopped: step limit reached before an answer."
```

Details that matter:

- **Append the assistant's full `content`**, including `tool_use` blocks (and thinking blocks, if
  present). The API needs each `tool_result` to match a `tool_use` from the previous assistant
  turn.
- **Handle multiple tool calls in one turn.** Models can request several tools at once (parallel
  tool use); return all results in a single `user` message.
- **Return tool output as text** (JSON is fine). Truncate large outputs before sending them back.

> [!TIP]
> Log every step: the tool name, input, a truncated output, tokens and timing. Printing the
> trajectory is the single best debugging tool for agents, and it is the seed of the tracing you
> add in session 9.5.5.

## Error handling and stopping conditions

Agents fail in more ways than single calls. Plan for each.

**Tool errors**: network failures, bad arguments, empty results. Don't crash the loop; return the
error to the model with `is_error: true` and a message it can act on. Models are good at recovering
("the search returned nothing, let me try different terms") if the message is clear.

```python
def execute(name: str, args: dict) -> tuple[str, bool]:
    fn = REGISTRY.get(name)
    if fn is None:
        return f"Unknown tool {name!r}. Available: {list(REGISTRY)}", True
    try:
        return json.dumps(fn(**args))[:4000], False     # cap output size
    except TypeError as e:
        return f"Bad arguments for {name}: {e}", True
    except Exception as e:                              # tool failure, not agent failure
        return f"{name} failed: {e}. Try different input or another approach.", True
```

**Unsafe tools**: never implement a calculator with `eval()`; the model's input is untrusted text
and `eval` executes arbitrary Python. Parse the expression with Python's `ast` module and allow only
numbers and arithmetic operators.

**Stopping conditions**, because a model's "I'm done" is not enough:

| Condition | Why |
| --- | --- |
| Model answers without a tool call | normal success |
| Max steps (for example 10-20) | prevents infinite loops |
| Token or cost budget | prevents surprise bills |
| Wall-clock timeout | keeps latency bounded |
| Repeated identical tool calls | detects loops ("search X" five times) |
| `stop_reason == "max_tokens"` | the response was cut off: raise the limit or stop |

When a limit hits, return a clear partial result ("Stopped after 10 steps; here's what I found so
far") rather than an exception, and log it so you can see how often it happens.

**API errors** (429, 5xx) are handled by the SDK's retries (session 9.1.5). A long agent run should
also survive a crash: if the run matters, persist `messages` after each step so it can resume.

> [!WARNING]
> Context grows with every step, so cost per step grows too: step 10 resends everything from steps
> 1-9. Keep tool outputs short, and for long runs consider clearing old tool results (context
> editing) or summarising.

## Practice: a research agent with web search and a calculator

Build a CLI research agent that answers questions requiring both current facts and arithmetic.
About two to three hours.

### Step 1: Implement the tools

- `web_search(query)`: use any search API you have access to (many offer free tiers), or fall back
  to fetching a fixed list of pages and searching them locally. Return at most five results with
  title, URL and a snippet under 300 characters.
- `calculator(expression)`: a safe evaluator using `ast`:

```python
import ast, operator as op
OPS = {ast.Add: op.add, ast.Sub: op.sub, ast.Mult: op.mul, ast.Div: op.truediv,
       ast.Pow: op.pow, ast.USub: op.neg}

def calculator(expression: str) -> float:
    def ev(n):
        if isinstance(n, ast.Constant) and isinstance(n.value, (int, float)):
            return n.value
        if isinstance(n, ast.BinOp) and type(n.op) in OPS:
            return OPS[type(n.op)](ev(n.left), ev(n.right))
        if isinstance(n, ast.UnaryOp) and type(n.op) in OPS:
            return OPS[type(n.op)](ev(n.operand))
        raise ValueError("only numbers and + - * / ** are allowed")
    return ev(ast.parse(expression, mode="eval").body)
```

Even this allows `9 ** 9 ** 9`, which never finishes: reject exponents above, say, 100 before
calling `op.pow`. Write three unit tests for the calculator, including one proving
`__import__('os')` is rejected.

### Step 2: Write the loop

Use the loop above with `max_steps=10`, a budget of 50,000 total tokens (sum `usage` across
steps), a 120-second timeout and repeated-call detection.

### Step 3: Print the trajectory

For each step print the step number, tool, input, the first 100 characters of output, and
cumulative tokens. Save the full `messages` to `runs/<timestamp>.json`.

### Step 4: Test with real questions

Try questions like "What is the population of the three largest cities in Italy combined?" or
"If I invest 200 euros a month at the current ECB deposit rate for 5 years, how much interest do I
earn, roughly?". Check: did it search before answering? Did it use the calculator for every
number? Are URLs cited?

### Step 5: Break it on purpose

Make `web_search` fail randomly 30% of the time and confirm the agent recovers. Ask an impossible
question and confirm it stops gracefully. Note the step count and cost for each run; you'll compare
them after adding tracing and approval gates in 9.5.5.
